# Multi-vector (ColBERT) benchmark: libembedding vs pylate (T14 complement, LE-11) - 2026-11-22

`libembedding.MultiVectorEmbedding` (ONNX Runtime) against pylate (PyTorch, the reference
implementation) on the same model, plus the MaxSim kernel against numpy. Script:
`bench_multivector.py`. Raw data: `results.json`.

## Conditions

| Field | Value |
|---|---|
| Machine | Intel i7-1065G7 (4 cores / 8 threads, AVX-512), Windows 11, on mains, quiet machine (nothing else running) |
| Code | libembedding dev branch at commit 0a70496 (Release build of the working tree, `LIBEMBEDDING_LIBRARY`), Python binding from `python/src` |
| Libraries | pylate 1.6.0, torch 2.11.0+cpu, numpy 2.5.5; the Python `onnxruntime` 1.32.0 of the venv is installed but libembedding uses its own bundled ONNX Runtime 1.31.0 |
| Model | answerai-colbert-small-v1 (dim 96): ONNX file for libembedding, `lightonai/answerai-colbert-small-v1` weights for pylate |
| Lengths | query 32, document 300, FP32; query expansion explicitly on for both (the model's own default is off) |
| Corpora | `short`: first 1000 lines of `benchmarks/datas/customers_sample.txt`; `long`: first 1000 BEIR SciFact documents (title + abstract, mean 236 vectors); `queries`: first 1000 SciFact queries (query mode) |
| Batch / threads | 1 and 32 / library default (libembedding 0 = auto, torch default) |
| Protocol | one process per measurement, warmup on 20 texts, 3 timed passes (median), 3 rounds with the library order rotated, median of the rounds |
| Tokens | tokens/s counts the tokens fed to the model (same `tokenizer.json` for both libraries, document truncated at 300, query padded to 32); vectors/s counts the vectors returned |

## Reading

- Embedding: libembedding is faster than pylate in every cell. The gap is largest where
  per-call overhead dominates: batch 1 on short texts (3.0x) and queries (2.1x). At batch 32
  on long documents, where the transformer compute dominates, the gap shrinks to 14 %
  (10.8 against 9.5 documents/s), which is of the order of what ONNX Runtime and PyTorch
  differ by on the same graph.
- Load time: 0.85 to 1.2 s against 8.3 to 8.8 s (torch and pylate import included).
- Memory: peak RSS 247 MB (short) to 493 MB (long documents) against 553 to 1021 MB.
- Storage: both libraries return identical shapes; a short text costs 4.8 KB, a SciFact
  abstract 88.6 KB (236 vectors x 96 x 4 bytes).
- Fidelity: same vector counts and MaxSim scores within 6e-6 of pylate; the ranking is
  identical.
- MaxSim: the kernel is a plain single-threaded C loop. On long documents (236 vectors)
  numpy (BLAS matrix product) scores 14.6 k pairs/s against 10.5 k for libembedding's
  `maxsim` loop (-28 %) and 7.7 k for `maxsim_batch` (-47 %). Two causes, analysed from the
  code (not profiled): the kernel `include/libembedding/similarity.h:131-145` is a scalar
  dependent-chain loop that the compiler cannot vectorise without fast-math, against
  numpy's BLAS matrix product; and `python/src/libembedding/similarity.py:96-98`
  concatenates all documents into a new buffer on every call (about 90 MB on long
  documents), which is why the batch call is slower than the loop. Fixes are being done in
  other branches; these files are untouched here. On short documents (13 vectors) the three are within run-to-run noise.

## Gaps above 20 %

| Cell | Gap | Explanation |
|---|---|---|
| short, batch 1 / batch 32 | +203 % / +51 % in favour of libembedding | Per-call overhead of the PyTorch path (tokenization in Python, padding, autograd-free but dispatch-heavy forward); short texts leave little compute to amortise it. Not profiled. |
| queries, batch 1 | +108 % | Same as above. |
| long, batch 1 | +29 % | Mixed: overhead plus ONNX Runtime kernels on 300 tokens. |
| MaxSim long documents | -28 % (loop), -47 % (batch) against numpy | Scalar dependent-chain loop against BLAS, plus the concatenation copy for `maxsim_batch` (see Reading). Fixes in other branches. |

## Limits

- One machine (i7-1065G7, 4 cores); no conclusion for ARM, AMD or more cores.
- pylate and libembedding use different weight formats (PyTorch against ONNX FP32); the
  scores agree to 6e-6 so the model is the same, but the runtimes differ by design.
- Disturbed cells (within-process spread of the 3 passes above 10 %): 10 of the 54 cells,
  flagged here rather than re-run because the machine was needed for other work. They are
  libembedding short batch 1 (35 %; 108 to 140 texts/s across rounds), pylate short batch 32
  (12 %), libembedding long batch 1 (11 %) and seven MaxSim cells (12 to 35 %, each pass lasts
  only milliseconds). The median of three rounds is reported with its range; the embedding
  conclusions do not depend on these cells, and the MaxSim ranking (numpy ahead on long
  documents) holds in every round.
- Query expansion was forced on for both libraries; the model's default (off) was not
  measured.
- Threads are the library defaults (not swept). MaxSim is measured single-query,
  single-thread.
- No GPU, no index or search (out of scope for the library).
